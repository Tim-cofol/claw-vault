# 用户需求说明
## 项目名称
EDN Strategic Intelligence System（ESIS）

---

## EDN 领域分类（当前工作版本）

本分类用于组织 ESIS 的情报采集、信号归类、竞争对比与后续能力映射。它描述 EDN 的业务/客户价值领域，不等同于当前产品授权包、研发版本或组织边界；具体 JOB、能力与商业化边界将在后续版本继续校准。

| 编号 | EDN 领域 | 对应服务线 | 核心价值与关注对象 |
| --- | --- | --- | --- |
| D1 | 网络统一管控与数据平台 | S1 | 面向多园区、多厂商、有线/无线/光/WAN 网络的统一纳管、自动开局、可视化、运维协作与可靠部署，是其余领域的管理与数据底座。 |
| D2 | 多网多业务安全隔离 | S2 | 面向多业务共网承载场景，以网络自动化编排、业务隔离、服务链编排和网络韧性保障业务安全与稳定。 |
| D3 | 身份与业务访问策略随行 | S3 | 面向人员、角色、位置与安全域变化，实现跨园区、跨异构环境的一致访问权限与流程化策略自动化。 |
| D4 | 关键业务体验与质量保障 | S4 | 从用户、关键应用和关键区域视角洞察网络与音视频等业务体验，推进预测、诊断、优化和自愈。 |
| D5 | 广域网、分支与云边连接 | S5 | 覆盖 SD-WAN/SD-Branch、混合链路、分支快速开局、应用调度、出口安全与跨园区端到端连接体验。 |
| D6 | 人与物的身份准入治理 | S6 | 面向人员、受管终端与哑终端，以身份识别、可信准入、访问控制和持续治理，确保不同对象在正确的网络、时间和权限范围内接入。 |
| D7 | 统一基础设施运营 | S7 | 面向网络及其关联基础设施的全生命周期运营：资产、配置与变更、软件维护、容量、可靠性、自动化与跨域协同，形成统一运营体系与可持续服务能力。 |
| D8 | 企业运营价值 | 新增 | 把网络技术能力翻译为企业经营结果：建设与运维成本、资源/带宽/能耗效率、业务开通效率、生产率、风险与 SLA、投资回报及订阅运营成效。该领域横向贯穿 D1–D7。 |

分类使用原则：

- D1–D7 用于标记“技术/产品能力主要落在哪个 EDN 领域”。
- D8 用于标记“该能力或事件为客户创造了什么可量化的企业运营价值”，可与任一 D1–D7 同时关联，不能被当作孤立产品线。
- S2 与 S3 在当前定义中分别独立：前者聚焦多网多业务的隔离与编排，后者聚焦身份/权限随人、角色和位置变化的一致性访问。
- S6 已明确为“人与物的身份准入治理”；其后续需进一步厘清人与终端身份绑定、哑终端识别、准入控制、风险处置及与 S3 策略随行的边界。
- S7 聚焦“统一基础设施运营”，与 S1 的边界是：S1 提供统一管控与数据底座，S7 关注基于该底座进行全生命周期、跨域和服务化运营的结果。

### EDN 扩展观察领域

S1–S7 是当前 EDN 的主业务领域，但 ESIS 的外部情报范围不应受现有服务编号限制。以下领域暂不映射为新的 S 服务线，作为独立的战略雷达和竞争观察维度：

| 编号 | 扩展领域 | 重点观察范围 | 与主领域的关系 |
| --- | --- | --- | --- |
| X1 | 数据中心与云网络 | 数据中心网络架构、网络虚拟化与自动化、多云/混合云连接、应用与数据跨云流动、云网策略一致性。 | 补足 D5 的广域与云边连接，不与其重复定义分支连接能力。 |
| X2 | 工业 OT 与 IIoT 网络 | 工业交换与路由、工业无线、现场资产连接、IT/OT 融合、确定性/高可用网络、OT 可视化与远程运维。 | 是 D6“物的身份准入”、D2“隔离”和 D7“运营”在工业场景中的延展。 |
| X3 | 安全与零信任运营 | SSE/SASE、远程安全接入、持续风险评估、威胁检测与响应、安全可观测性、合规运营。 | 与 D2/D3/D6 的“网络内控制”互补，聚焦跨网络、云和安全域的持续安全运营。 |
| X4 | 新型企业网络架构与基础技术生态 | 园区 Fabric、白盒网络、以太网/交换标准、网络芯片与硅生态、遥测与数据平台，以及新兴企业网络架构。 | 作为 D1、D5、D7 的底层技术与生态观察维度，用于捕捉架构范式和供应链变化。 |

横向主题不单独编号为领域：网络 AI 运维（Network AIOps）、可观测性、DEX/DEM、数字孪生、自主运营、Agentic AI、身份与 NAC、策略编排、遥测/数据平台、网络自动化与可编程性、园区 Fabric、SD-WAN、NaaS、安全网络融合、无线与移动性、云托管运营。它们应作为 D1–D7 及 X1–X4 的标签，用于识别技术趋势、竞品押注与能力演进，避免形成互相重叠的领域树。

扩展领域和横向主题必须根据厂商信号、标准演进和市场变化动态增删；每次调整须说明新增、合并、拆分或移除的原因及证据。

## 1. 需求背景

用户希望构建一套面向 **Enterprise Networking / EDN 战略分析** 的情报系统，用于持续跟踪行业动态、竞争厂商动作、技术社区信号与早期舆情，并自动生成高质量的 **Strategic Radar（战略雷达）**，为 EDN 战略规划、技术方向判断和竞争分析提供输入。

用户当前的核心诉求不是一次性构建完整的大系统，而是先快速落地一个 **可运行、可持续产出结果** 的第一阶段能力。

---

## 2. 总体目标

系统总体目标如下：

1. 持续跟踪 Enterprise Networking 行业和关键竞争厂商动态。
2. 自动收集多源外部信息并进行筛选、合并、去重和评分。
3. 每天生成一份高质量的 **EDN Strategic Radar**。
4. 输出真正重要的行业信号，而不是普通新闻聚合。
5. 后续逐步扩展为支持内部研发、客户需求和能力差距分析的完整战略情报系统。

---

## 3. 当前阶段建设要求

### 3.1 第一阶段（v1）
第一阶段系统定位为：

**External Intelligence Engine**

v1 仅实现 **外部行业情报能力**。

#### 深度研究基本原则

- 每个研究周期必须主动从 Web 获取最新公开数据并提供可访问的来源链接/引用；不得仅依赖记忆、历史摘要或未验证的二手转述。
- 优先使用一手来源和可信英文来源；华为、H3C 等厂商在英文一手来源不足时，可补充其中文官方来源。
- 每条证据必须标注来源类型：官方、技术媒体、分析师/市场、财务、客户/社区、标准/生态，或“支撑假设的弱信号”。
- 必须区分硬事实、评论观点和推断信号：事实应可由来源直接验证；评论应注明作者/机构立场；推断必须披露推理前提与不确定性。
- 结论须由本轮可追溯证据支持；无充分证据时，明确标注为假设或待验证项。

#### v1 必须实现的能力
- 多源外部信息采集
- 多源信息合并
- 基础去重
- 内容过滤
- AI 评分
- Strategic Radar 生成
- Competitive Gap Analysis（竞争差距分析）：基于外部公开信息，对关键厂商的能力、产品定位与战略动作进行对比。
- Trend Prediction（趋势预测）：从持续积累的行业、竞品与技术信号中识别趋势，并给出方向、置信度与依据。
- Strategic Simulation（战略推演）：基于外部信号和显式前提，对机会、风险与竞争情景进行推演，输出可供讨论的战略假设。

#### 厂商覆盖要求

每个研究周期必须并行监测以下厂商；当出现重要新进入者、相邻赛道厂商或区域性竞争者时，应动态纳入：

- Cisco
- HPE Aruba Networking
- Juniper Mist
- Arista
- Huawei
- H3C
- Extreme Networks
- Fortinet
- Zscaler
- Palo Alto Networks
- Nile

#### 每周期必做研究维度

| 维度 | 必须关注的内容 |
| --- | --- |
| 产品动态 | 产品发布、版本/功能变化、架构方向、集成关系和路线图信号。 |
| 技术动态 | 网络 AI 运维、零信任/SASE、可观测性、园区 Fabric、白盒网络、以太网标准、网络芯片、自动化与 Agentic Operations。 |
| 市场动态 | 客户需求、渠道/伙伴变化、定价与许可、竞争定位、分析师观点、财报信号、并购、融资、市场份额、客户采用和采购方优先级。 |
| 服务与 GTM 动态 | NaaS、托管服务、支持模式、CX/客户成功、伙伴生态、垂直行业方案及 land-and-expand（先落地后扩展）模式。 |

#### v1 输出目标
- 每个研究周期（默认按日执行）识别并输出 **5–10 条最重要行业信号**

## 4. v1 范围边界

### 4.1 v1 包含范围
v1 仅处理外部行业情报，具体包括：
- 厂商官方信息
- 行业媒体内容
- 厂商在 YouTube 上发布的更新、技术分享与趋势信号
- 技术社区与 GitHub release
- X（Twitter）上的早期信号、观点、社区反应与链接传播

### 4.2 v1 不包含范围
以下内容明确不在 v1 当前范围：
- 内部研发进展
- 产品 roadmap
- 客户需求
- 售前反馈
- 内部能力对比

竞争差距分析、趋势预测与战略推演属于 v1 必实现能力，但其分析输入限于外部公开信息与明确记录的推演前提。

## 5. 实现原则

- 不限定具体技术形态或实现载体，由工程设计根据当前需求选择合适方案。
- 当前阶段避免过度工程化，优先快速实现可运行、可持续产出的能力。
- 优先跑通“每日战略雷达”及其竞争差距分析、趋势预测、战略推演闭环。
- 不以预先建设复杂数据库或复杂情报平台为前提。

## 7. 数据源要求

系统必须覆盖多种外部来源类型，用于形成对行业、竞品、趋势和观点的综合判断。每次研究均应优先获取当期一手公开资料；所有引用须标明发布日期、来源类型、厂商、领域和研究维度。

来源类型统一标记为：

- **官方**：厂商、交易所、监管或客户官方发布的一手资料。
- **技术媒体**：专业技术媒体、行业记者或技术播客的报道与分析。
- **分析师/市场**：分析机构、市场研究、渠道和采购视角资料。
- **财务**：财报、业绩会、融资、并购、估值和市场交易信号。
- **客户/社区**：客户案例、用户评价、开发者/运维社区和伙伴反馈。
- **标准/生态**：标准组织、开源项目、专利、芯片和供应链生态资料。
- **支撑假设的弱信号**：无法单独证实结论、但可用于提出待验证假设的线索；不得作为确定性事实的唯一依据。

- Extreme Networks
- Huawei

### 7.3 YouTube 来源
系统必须纳入厂商在 YouTube 上发布的内容，原因是这些内容中存在大量：
- 技术分享
- 产品演示
- 方案讲解
- 大会演讲
- 趋势释放
- 新方向信号

YouTube 是识别趋势和方向的重要来源，尤其适合捕捉：
- 新能力方向
- 技术叙事变化
- 未来路线信号
- 对市场教育的重点变化

应重点关注：
- 厂商官方频道
- 产品团队相关频道
- 技术布道类内容
- 大会演讲视频
- 产品更新说明视频

### 7.4 X（Twitter）来源
X 必须纳入 v1 数据源体系。

X 中的信息可以包括：
- 观点
- 社区反馈
- 趋势发酵信号
- 产品发布线索
- 官方账号发布内容
- 指向官方博客、文档、新闻、视频等内容的链接传播

必须支持以下对象类型：
- Vendor official accounts
- Product leaders
- Networking analysts
- Technical influencers
- Conference hashtags

X 在系统中的作用包括：
- 早期信号来源
- 社区观点来源
- 趋势放大来源
- 官方链接传播入口

对于 X 内容，系统需要进行更强过滤，重点保留：
- 产品发布线索
- 新能力讨论
- 大会演示相关内容
- 高可信账号的专业判断
- 社区对重要更新的反馈
- 指向厂商官方页面、文档、博客、新闻、YouTube 的链接

X 上的信息不应一概视为低可信来源。  
如果 X 内容本身来自厂商官方账号，或者 X 内容中包含官方链接、官方发布、官方文档、官方视频等可验证内容，则它同样可以构成可靠来源。  
因此，系统应根据内容本身及其指向来源来判断可信度，而不是仅按平台一刀切。

### 7.5 GitHub 来源
系统应支持：
- GitHub releases
- Open source networking projects
- Observability / automation tools

GitHub 在系统中的作用主要是：
- 补充技术变化信号
- 补充开源生态变化
- 识别网络自动化、可观测性、工具链方向的更新

GitHub 不是厂商动态的主要来源，但属于需要覆盖的补充来源类型。

### 7.6 B 类财务与市场来源

当需要验证商业化、竞争强度或市场变化时，可按相关性使用以下 B 类来源，并以财报、业绩会记录、监管披露等一手材料优先交叉验证：

- Investopedia
- Seeking Alpha
- Crunchbase
- Owler
- Business Insider
- Barron's
- The Motley Fool 的业绩会文字稿
- 厂商财报及业绩会文字稿
- Fierce Telecom 的以太网交换机市场报道

此类来源用于发现融资、并购、估值、收入、许可模式和市场叙事信号；未经一手资料或多源交叉验证的观点不得直接写成硬事实。

## 8. 系统核心处理流程要求

### 8.1 原始完整处理思路
用户最初提出的完整处理流程为：

Sources  
↓  
Collectors  
↓  
Raw Documents  
↓  
Event Extraction  
↓  
Event Deduplication  
↓  
Event Clustering  
↓  
Capability Mapping  
↓  
Topic Classification  
↓  
Event Scoring  
↓  
Strategic Signal Detection  
↓  
Daily Strategic Radar

### 8.2 v1 深度研究循环

每个研究周期按以下闭环执行：

研究范围校准（厂商、主领域、扩展领域、横向主题）  
↓  
主动获取当期公开 Web 数据  
↓  
证据标准化（日期、厂商、领域、研究维度、来源类型、链接）  
↓  
事实/评论/推断信号分类与来源可信度评估  
↓  
事件抽取、合并、去重、聚类与重要性评分  
↓  
产品、技术、市场、服务/GTM 四维分析  
↓  
跨厂商模式识别与竞争差距分析  
↓  
趋势预测、战略推演与置信度评估  
↓  
EDN Strategic Radar

即：

- v1 不强制先实现完整事件数据库或能力图谱，但必须保留每项关键结论的证据链接和分类元数据。
- v1 不是“资讯收集 + 摘要”，而是基于可追溯证据的深度研究循环。
- v1 重点是稳定生成高质量战略雷达和可讨论的战略判断，而不是先把底层系统做成航母。

## 9. 输出要求

### 9.1 输出名称
每个研究周期生成一份：

**EDN Strategic Radar**

### 9.2 输出格式
- Markdown。
- 全文必须使用专业的简体中文；产品名、技术术语、标准和专有名词可保留必要英文。
- 所有关键事实和数据点必须包含来源链接/引用；不得以无来源的记忆性摘要替代当期证据。

### 9.3 深度与证据要求

- 每次输出应识别 **5–10 条最重要行业信号**，并给出具体日期、产品名、能力变化及可获得的客户、市场或财务信号。
- 输出重点是“为什么重要”和战略含义，不得写成普通新闻摘要。
- 对证据不足的判断必须明确标为“假设”“弱信号”或“待验证”，不可与已证实事实混写。

---

## 10. Radar 结构要求

每份 Radar 必须按以下结构输出：

### 10.1 执行结论

给出 3–5 条 EDN 战略结论，而不是新闻摘要。每条结论应说明其证据基础、战略影响和主要不确定性。

### 10.2 证据地图

逐项列出本轮关键数据点，至少包含：来源监控 ID、日期、厂商、领域/主题、研究维度（产品/技术/市场/服务与 GTM）、来源类型、事实/评论/推断标记、原始页面链接/引用及简要说明。

### 10.3 市场动态

分析采购方需求、渠道动作、融资/并购、业绩会信号、定价/许可、采用信号和竞争叙事。

### 10.4 厂商动态

按厂商说明“发生了什么、为什么重要、最可能的战略意图是什么”。重点覆盖本轮有实质变化的厂商，不以固定厂商清单凑篇幅。

### 10.5 领域演进

说明网络 AI 运维、零信任/SASE、可观测性、园区 Fabric、DEX/DEM、NaaS、以太网/交换、网络芯片、白盒网络和 Agentic Operations 等主题如何变化；必要时新增或调整扩展领域。

### 10.6 跨厂商模式识别

识别收敛、分化、白区、弱信号和非显性的战略动作，并说明其证据和反例。

### 10.7 对 EDN 的影响

从架构影响、产品能力差距、GTM/服务影响、差异化机会和竞争风险五个方面给出判断。

### 10.8 建议行动

分别提出近期、中期和长期行动建议；建议必须能回溯到前述证据或明确标注的推演前提。

### 10.9 置信度与未知项

明确区分“证据支撑的结论”“合理推断/假设”和“待验证未知项”，并给出整体或逐项置信度。

## 11. 工程复杂度要求

v1 必须避免过度工程化。

要求如下：
- 不要复杂数据库
- 不要 capability graph
- 不要内部数据接入
- 优先跑通
- 第一阶段重点是生成高质量 daily radar，而不是构建完整大系统

---

## 12. 成功标准

v1 成功标准如下：
- 每个研究周期稳定生成可追溯的 EDN Strategic Radar
- 关键结论均有当期公开来源链接和明确的来源类型标记
- 能够清晰区分硬事实、评论观点、推断信号与未知项
- 能输出有证据支撑的竞争差距、趋势预测、战略推演与行动建议
- 信号质量高，噪音比例低

ESIS v1 的目标不是：

**新闻聚合**

而是：

**Enterprise Networking Intelligence Engine**

它需要每天自动发现：
- 行业变化
- 竞争信号
- 技术趋势

并为：

**EDN 战略规划**

提供持续输入。

系统将逐步演进为：

**Enterprise Networking Strategic Intelligence Platform**

最终能够每天自动回答：
- 今天行业最重要的变化是什么
- 竞争厂商在押注什么能力
- 哪些方向值得关注

## 15. 结论

本需求说明完整覆盖以下用户要求：
- v1 只做外部情报
- 每个研究周期必须主动获取当期公开 Web 数据并引用来源，不能只依赖记忆或历史摘要
- 数据源必须覆盖厂商官方博客、新闻、网站更新、文档更新、行业媒体、YouTube、X、GitHub，并按相关性补充分析师、财务、客户/社区和标准/生态资料
- 厂商官方来源是主要事实来源
- GitHub 属于补充来源
- YouTube 必须纳入，因为厂商技术分享和趋势表达很多在那里
- X 必须纳入，不仅承载观点，也可能承载官方发布链接和可靠信息传播
- 输出必须是 Markdown 格式的 EDN Strategic Radar
- 输出必须使用专业简体中文，并保留必要英文产品名、技术术语、标准和专有名词
- Radar 必须包含执行结论、证据地图、厂商动态、领域演进、市场动态、跨厂商模式识别、EDN 影响、建议行动及置信度与未知项
- 竞争差距分析、趋势预测与战略推演必须纳入当前实现范围
- 第一阶段必须避免过度工程化
